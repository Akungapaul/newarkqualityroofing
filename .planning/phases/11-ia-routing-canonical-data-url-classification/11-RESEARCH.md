## Summary

This is a **spec-driven recon phase**. Every WHAT and target path is LOCKED by `.planning/IMPLEMENTATION-PLAN.md` (D-01..D-15). The research goal was to map the REAL codebase so plans target actual files/signatures and to surface technical landmines. **All locked counts in D-03/D-05 are exactly reproducible from `URL-Classification.csv`** — verified by computation below: combo KEEP **255**, combo NOINDEX **942**, combo CONSOLIDATE/301 **168** (sum = 1,365), plus **8** legacy hub redirects. The verdict-validation assertion the build needs is therefore deterministic and safe to fail-hard on.

The site today is served by a **single flat dispatcher** `src/app/[slug]/page.tsx` with `dynamicParams = false`, fed by an in-memory `src/data/slug-registry.ts` Map (collision-checked at module load) and `getAllSlugs()` in `generateStaticParams`. Combos are generated by `src/data/combos.ts` as **65 services × 21 cities = 1,365** (the registry's "63×21=1,323" comment is STALE — actual is 1,365, matching the CSV). Sitemap uses the modern `generateSitemaps()` multi-file API; robots/noindex is handled only in `generateMetadata` per-page (`NOINDEX_PAGES` set). The current `src/data/site-config.ts` literally hardcodes the fake trust values D-01 forbids (`500+`, `15+`, `5.0`, `(973) 555-0123`, `123 Main Street`), and `src/lib/schema.ts` hardcodes a fake `AggregateRating` of `5.0`/`500` — both are the targets of the D-01 consolidation (full enforcement is Phase 16, but Phase 11 creates the canonical source + sets `rating.enabled=false`).

**Primary recommendation:** Build the generator (`scripts/build-url-classification.ts`) as a **prebuild `tsx` step** that parses the CSV with a quote-aware parser, asserts the exact counts (255/942/168/8) and zero redirect chains, then emits `src/generated/url-classification.json` + `src/generated/redirects.generated.mjs`. Keep the **flat `[slug]` dispatcher** for combos (verdict-gated via the new verdict API) and add a **separate optional-catch-all** `app/roofing-knowledge-base/[[...slug]]/page.tsx` plus a **dedicated** `app/roofing-glossary/page.tsx` — both with `dynamicParams=false` and enumerated `generateStaticParams`. Collision-free because the KB/glossary routes are at distinct path prefixes that the flat `[slug]` segment never claims.

### Pattern 1: Optional-Catch-All with enumerated `generateStaticParams` + `dynamicParams=false`
**What:** A single `[[...slug]]` segment renders the index (no params), the 6 cluster hubs (1 segment), and the 44 nested articles (2 segments). `dynamicParams=false` makes anything not enumerated 404.
**When to use:** D-10 nested KB route.
**Example:**
```typescript
// app/roofing-knowledge-base/[[...slug]]/page.tsx
// Source: nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes (optional catch-all)
export const dynamicParams = false; // [CITED: nextjs.org/.../generate-static-params]

const CLUSTERS = ['roof-problems','roof-components','roofing-materials',
                  'roofing-process','roofing-costs','local-roofing-knowledge'] as const;

export async function generateStaticParams() {
  return [
    { slug: undefined },                                  // /roofing-knowledge-base  (hub — optional segment empty)
    ...CLUSTERS.map((c) => ({ slug: [c] })),              // /roofing-knowledge-base/{cluster}  (6 cluster hubs)
    ...KB_ARTICLES.map((a) => ({ slug: [a.cluster, a.slug] })), // /…/{cluster}/{slug}  (44 nested articles)
  ];
}
```
> NOTE on the empty hub param: for an **optional** catch-all the index path is produced by `{ slug: undefined }` (some Next versions also accept `{ slug: [] }`). The planner should have the executor verify which the installed Next 16.1.6 build accepts during dev; both are documented patterns. `params.slug` arrives as `string[] | undefined` and the page branches on `slug?.length` (0/undefined = hub, 1 = cluster, 2 = article). `[VERIFIED: nextjs.org docs + computed enumeration of 51 paths]`

### Pattern 2: Generated redirects imported into `next.config.ts`
**What:** The generator emits an `.mjs` that `export default`s the redirect array; `next.config.ts` spreads it alongside the preserved redirects.
**Example:**
```typescript
// src/generated/redirects.generated.mjs  (emitted — do not edit)
export default [
  { source: '/full-roof-tear-off-newark-nj', destination: '/roof-replacement-newark-nj', permanent: true },
  // …175 more (168 combo + 8 legacy)
];

// next.config.ts
import generatedRedirects from './src/generated/redirects.generated.mjs';
const nextConfig: NextConfig = {
  trailingSlash: false, // PRESERVED (D-09)
  async redirects() {
    return [
      ...generatedRedirects,
      // PRESERVED existing:
      { source: '/flat-roof-installation-newark-nj', destination: '/flat-roof-installation-repair-newark-nj', permanent: true },
      { source: '/:path*', has: [{ type: 'host', value: 'www.newarkqualityroofing.com' }],
        destination: 'https://newarkqualityroofing.com/:path*', permanent: true },
      // NEW hub migrations (D-07):
      { source: '/services',  destination: '/roofing-services',        permanent: true },
      { source: '/locations', destination: '/service-areas',          permanent: true },
      { source: '/resources', destination: '/roofing-knowledge-base',  permanent: true },
    ];
  },
};
```
> `[VERIFIED: CSV redirect targets are root-relative slugs]` — the CSV's `Redirect Target` column is already `/roof-replacement-newark-nj` form (leading slash, no domain), exactly what `destination` wants. **`source` must be the URL minus the domain** (strip `https://newarkqualityroofing.com`).

### Pattern 3: Combo verdict gate inside the flat dispatcher
**What:** The existing combo branch in `app/[slug]/page.tsx` consults the verdict API to set robots/404. Redirects are handled by `next.config.ts` (so a redirected combo slug should NOT be in `getAllSlugs()` → it 404s at the route level but the redirect fires first).
**Example:**
```typescript
// generateMetadata, combo case — ADD:
import { isNoindex } from '@/data/url-classification';
// …
return {
  title: combo.metaTitle, description: comboDescription,
  alternates: { canonical: `/${combo.slug}` },              // keep = self-canonical (D-04)
  robots: isNoindex(combo.slug) ? { index: false, follow: true } : undefined, // 942 noindex,follow (D-04)
  openGraph: buildOG(...),
};
```

### Anti-Patterns to Avoid
- **Handling 301 combos via the route/404 path instead of `next.config.ts`.** Redirects MUST be config-level so they fire before route resolution (precedence: redirect > 404). Don't `redirect()` inside the page component for the 168 — that runs after a 200 render attempt.
- **Canonicalizing noindex combos to an unrelated page.** D-04 says noindex = `noindex,follow` + self/no canonical. Never point a noindex combo's canonical at its keep "parent."
- **Letting `validate-flat-urls.ts` fail on KB nested slugs.** That existing validator (`scripts/validate-flat-urls.ts`) rejects any slug containing `/`. The nested KB route does NOT go through the flat slug-registry, so it's fine — BUT if the planner registers KB articles in the same registry with `/` in the slug, this validator will fail the build. Keep KB paths out of the flat registry OR update the validator. (See pitfall 4.)
- **Trusting the registry comments.** `slug-registry.ts` comments say "1,323 combos / 252 articles / 7 core" — all STALE. Real: **1,365 combos, 252 articles, 9 core pages.**

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 301 redirects | Per-page `redirect()` calls or middleware | `next.config.ts` `redirects()` | Config redirects fire at server/edge before routing, are cacheable, and respect precedence. 178 total redirects is far under Vercel's 1,024 limit. `[CITED: nextjs.org redirects docs — Vercel 1,024 limit]` |
| Multi-sitemap generation | Manual XML string building | `generateSitemaps()` (already in `app/sitemap.ts`) | Next 15+/16 native multi-file sitemap API; just filter the `combos` case by `isKeep()` |

## Common Pitfalls

### Pitfall 1: `next.config.ts` imports `redirects.generated.mjs` that doesn't exist yet (chicken-and-egg)
**What goes wrong:** `next build` loads `next.config.ts` first; if it statically imports the generated `.mjs` and that file hasn't been generated, the build crashes before compiling pages.
**Why it happens:** The generator is a prebuild step but the import is at config-load time.
**How to avoid:** Add `"prebuild": "tsx scripts/build-url-classification.ts"` so npm runs it before `build` automatically, AND commit the generated artifacts so a fresh checkout builds. Alternatively use `async redirects() { const r = await import(...); ... }` with a fallback to `[]` if missing — but static import + committed artifact is cleaner and reviewable.
**Warning signs:** `Cannot find module './src/generated/redirects.generated.mjs'` at build start.

### Pitfall 2: Stale registry comments / count drift (252 vs 253 articles, 1,323 vs 1,365 combos)
**What goes wrong:** Planner trusts the spec's "253 articles" or the registry's "1,323 combos."
**Why it happens:** `articles.ts` actually defines **252** articles (`grep -c id` = 252; CSV "Knowledge base article" rows = 252). Combos are **65×21 = 1,365** (the registry's "63×21=1,323" comment is wrong; CSV confirms 1,365). The spec text says "253 existing articles" in D-14 — this is an **off-by-one in the spec language** (actual file + CSV both say 252).
**How to avoid:** The build cluster-validation should assert **`articles.length === 252` AND every article has a cluster** (not hardcode 253). Flag the 252-vs-253 to the user before locking (see Open Questions). Use the CSV-derived combo total (1,365) for the count assertion, NOT the registry comment.
**Warning signs:** A validator hardcoded to 253 fails against the real 252 articles.

### Pitfall 3: Naive CSV parsing corrupts columns
**What goes wrong:** `line.split(',')` breaks because the `Reason` column (col 9) contains quoted commas (e.g. `"Trust page — add NJ HIC number, fix testimonials, …"`).
**Why it happens:** RFC-4180 quoting.
**How to avoid:** Use a quote-aware parser. Mitigating factor: `Verdict`(7) and `Redirect Target`(8) precede the quoted `Reason`(9), so even a simple left-to-right quote-respecting scan that stops after col 8 is safe. Verified: the count computations in this research used quote-aware awk and produced exact 255/942/168/8.
**Warning signs:** Verdict counts off by a handful; targets containing fragments of reason text.

### Pitfall 4: Nested KB slugs vs `validate-flat-urls.ts`
**What goes wrong:** `scripts/validate-flat-urls.ts` fails the build on any slug containing `/`. If KB nested URLs are added to the flat slug registry, this validator (and the spirit of the flat-URL system) breaks.
**Why it happens:** The KB route is intentionally nested (`/roofing-knowledge-base/{cluster}/{slug}/`) — the ONLY nested URLs on the site.
**How to avoid:** Keep KB hub/cluster/article paths OUT of the flat `slug-registry.ts` (they live in the catch-all route's own enumerated data). If the registry must record them for collision/page-type purposes (D-13), update `validate-flat-urls.ts` to exempt `roofing-knowledge-base/*` paths. The planner must decide and make it explicit.
**Warning signs:** `validate:urls` fails with `roofing-knowledge-base/roof-components/what-is-roof-flashing`.

### Pitfall 5: Hub-migration redirect vs the new hub page (precedence)
**What goes wrong:** `/services` is both (a) a 301 source → `/roofing-services` AND (b) currently a real core page. If `/services` still exists as a page AND has a redirect, the redirect wins (good) — but the OLD `/services` core slug must be RENAMED to `roofing-services` (D-07 "update core slugs"), not left in place, or you get a self-referential mess.
**Why it happens:** D-07 both adds a redirect and renames the core slug.
**How to avoid:** Change the core-page slugs in `core-pages.ts` (`services→roofing-services`, `locations→service-areas`, `resources→roofing-knowledge-base`) so the canonical page lives at the new slug; add the 301 from the OLD path in `next.config.ts`. Verify the new slug doesn't collide with the 6 new hub scaffolds or the `[[...slug]]` KB route prefix (`roofing-knowledge-base` is the KB route prefix — `/resources → /roofing-knowledge-base` points the resources redirect at the KB hub, which is the catch-all index, NOT a core page; confirm that's intended — it is, per BRIEF line 9).
**Warning signs:** Slug collision thrown by `buildRegistry()`; `/roofing-knowledge-base` served by two routes.

### Pitfall 6: Fake trust values leak through `src/lib/schema.ts` (not just site-config)
**What goes wrong:** Setting `rating.enabled=false` in the new config does nothing if `src/lib/schema.ts:50-58 buildAggregateRating()` keeps hardcoding `ratingValue:'5.0', reviewCount:'500'` and `buildRoofingContractorSchema`/`buildLocalBusinessSchema` keep calling it.
**Why it happens:** AggregateRating is hardcoded in the JSON-LD builders, independent of site-config.
**How to avoid:** Full removal/gating of hardcoded JSON-LD trust values is **Phase 16**, but D-01 says no public placeholder/fake trust values may render in JSON-LD. The planner must decide the Phase-11 boundary: at minimum, the NEW `src/config/site-config.ts` must not emit fakes; whether Phase 11 also gates `buildAggregateRating()` is a scope call (CONTEXT D-01 says "Foundation; full enforcement is Phase 16"). **Recommendation:** In Phase 11, gate `buildAggregateRating()` behind `rating.enabled` (cheap, prevents a known-false `5.0`/`500` from rendering) — this satisfies "no fake ratings in JSON-LD" without doing the full Phase-16 dedup. Flag to user.
**Warning signs:** `5.0` / `500` still in page JSON-LD after Phase 11.

## Code Examples

### Verdict API consumer shape (D-02)
```typescript
// src/data/url-classification.ts
import classification from '@/generated/url-classification.json';
// classification: { keep: string[], noindex: string[], redirects: Record<string,string> }  (shape is Claude's discretion)

const keepSet = new Set(classification.keep);
const noindexSet = new Set(classification.noindex);
const redirectMap = new Map(Object.entries(classification.redirects));

export function getComboVerdict(slug: string): 'keep' | 'noindex' | 'redirect' | 'unknown' {
  if (redirectMap.has(slug)) return 'redirect';
  if (keepSet.has(slug)) return 'keep';
  if (noindexSet.has(slug)) return 'noindex';
  return 'unknown';
}
export const isKeep = (s: string) => keepSet.has(s);
export const isNoindex = (s: string) => noindexSet.has(s);
export const isRedirect = (s: string) => redirectMap.has(s);
export const getClassification = (s: string) => getComboVerdict(s);
export function getComboRedirects(): Array<{ source: string; destination: string; permanent: true }> {
  return [...redirectMap].map(([source, dest]) => ({ source: `/${source}`, destination: dest, permanent: true }));
}
```
